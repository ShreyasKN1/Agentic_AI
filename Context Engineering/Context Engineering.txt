Context Engineering:

Optimizing the use of token and ending up what we wanted in the outcome.
providing agent-right information at right time
prompt engineering is an subtype of context engineering

think about it yourself, prompt engineering is useful when we just want an answer to the question, like how we ask in normal chatgpt->we are trying to enchrich output with what we want
 but when we go with big picture like agents->agent might do the following to come to an output-> maybe browsing the cache, make some API calls, writing code where prompt engineering might not work


LLM{RAM}------> Context {fixed working memory that fills up fast for the agent}

As the problem builds itself, as ram fills up more-> performance of the system degrades
same context piles up, huge context degrades agent reasoning [context drop].

According to one of the blogs, since llm are based on transformers -> each token attends to next token within same context resulting in n power 2 pairwise relationship for n tokens.
like imagine a person trying to remember everything happened during couple of days, one might forget usful info.

What might be an agent context:
1)System prompts: instructions on what the system has to do, workflows, instructions to perform that flow, unresolved issues,what to do and what not to do.
2)Tool definitions: What schema & input parameter does the model expects [go through mcp or tool calling first before context engineering].
3)toolcall results: now what type of structured output we expect after tool executuion-> serliase ->llm and then output in whyat format.
4)RAG,retrived docs: docs,vectorStore, even API responses.
5)Conversation history: full contextual information.
6) Memory: there is whole repo made for memory related context you can go through it.
7)agent state/current plan-> how the tool is executed on certain tasks.

=>Let's see why agent fails and where the context engineering have to be given more importance to:
1) Context poisoning:
	Iterate output-> info passed on to the next step as input here, the fix is to add debugging at every layer and you can either make sure we create summaries if important or just get rid of old convos

2)Context distracting: 
	Long context history->agent stops thinking by itself and repeats based on the pattern that it saw recently, forgets what it was trained for and follows the recent bias
fix: here is to Summarizing and aggressively pruning even when the context window is huge 
remember quality of context>quantity of context.

3)Context confusion:
	multiple tools connected? 
there was a paper went through that one of the models with 46 tools failed in certain env but it passed when only 20 tools was connected it worked fine in the same environment.

fix: tool masking or rag-mcp[paper read].

4)Context clash: 
	Contradicting in the context provides inconsistent behaviour
	Example:
system prompt-> use metrics for calculating something.
retrieved docs/rag->use some other units.
user history-> he usually gets solution in inches or feet.

fix: Provide priority wherever necessary -> high for system prompts, mid for retrieved docs [give a check before] and low for history always.

All above by drew breunig's taxonomy paper.


Best Practices to keep in mind:
1)Specific enough for autonomous behaviour and also allow agent to think itself wherever necessary.
2)start minimal and iterate[write first draft-> test on real tasks-> find gap of error and rewrite].
3)minimal is not short[ there might be tasks that need long context/tokens so it's fine but make sure it is needed and one of the above doesn't fail].
4)Tool masking>tool removing[tool masking with k+v cache ,rag-mcp one of nthe best].
